Contains armory-config.php (the one-time credentials file), weapons.php (read API, marker weapons-read-v6), weapons-sync.php (write API, marker weapons-sync-v8), index.html (the console, BUILD 2026-10-19.3), weapons-upgrade.sql, and INSTALL.txt. The database password now lives only in armory-config.php — fill in its "pass" line once and upload it alongside the two endpoints; no PHP file has to be edited again, so an endpoint upload can never take the password with it. Verify the password before touching the live endpoints by opening /armory-config.php?check=1 on the subdomain — it answers {"success":true,"database":"connected"} or names the problem, and never prints the password.

If weapons.php already says "Database connection failed": the password was replaced by a placeholder, not lost from the database. Copy $db_pass from fleetregistry-api.php (or records.php) on the same Hostinger account — same MySQL user and database — into armory-config.php, upload it, and reload. The endpoint now answers "Database password not set. Open armory-config.php…" when the line is still blank, so the cause is named instead of guessed at.

One-time setup: open weapons-upgrade.sql from the extracted package in Notepad, copy all of it, and run it in phpMyAdmin (Hostinger → Databases → phpMyAdmin → u102692168_Star_Force → SQL tab → Go). It adds the images column the card renders. Safe to run twice.

October 19, 2026 — the "I saved it and the database did not change" fix. The weapons table has a UNIQUE index on registry_number, and every record with a blank registry number shares the one empty-string slot. The old sync used INSERT ... ON DUPLICATE KEY UPDATE, so a save could rewrite a different weapon, answer 201, and leave the record you edited untouched. POST now resolves the row by id first, stores blank registry numbers as NULL, and answers 409 on a real clash instead of overwriting. The read endpoint now answers the browser's CORS preflight (OPTIONS) instead of rejecting it with 405 — that rejection was why the front end said Failed to fetch while the same URL returned data to curl. It also adds Cache-Control: no-store so the front end cannot replay an arsenal from before the save. Credentials moved out of both endpoints into armory-config.php, so this upload cannot repeat the outage that followed the last one. Upload the config, both PHP files, and the console, then hard-refresh.

Earlier: images on the front-facing weapon card (the console's picture now persists through the API instead of staying in one browser's localStorage), image downscaling to stay under upload limits, JSON-string tolerance in the card so a partially deployed server still renders.

Console only (BUILD 2026-10-19.3): download this file (it saves as armory-console.html), upload it to the armory.starforcebase1198.com web root without renaming it, then open armory.starforcebase1198.com/armory-console.html.
