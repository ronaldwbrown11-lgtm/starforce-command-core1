WHAT WAS BROKEN AND WHAT CHANGED
--------------------------------
v8 (weapons-sync.php) - POST no longer uses INSERT ... ON DUPLICATE KEY UPDATE.
    The weapons table has a UNIQUE index on registry_number, and every record
    with a blank registry number shares the single empty-string slot. The old
    statement therefore rewrote whichever weapon held that slot and still
    answered 201, so a save could report success while the record you edited
    never changed and a different weapon was overwritten. POST now looks the
    row up by id and updates it, inserts only when the id is genuinely new,
    stores a blank registry number as NULL (NULLs do not collide), and answers
    409 instead of silently overwriting on a real registry-number clash.
    PUT/DELETE were already keyed on id and are unchanged.

v6 (weapons.php) - answers the CORS preflight. The site's armory browser sent
    a "Cache-Control" request header, which is not CORS-safelisted, so the
    browser first asked with OPTIONS. This endpoint answered 405 with no
    Access-Control-Allow-* headers, so the browser cancelled the real GET and
    the page showed "Failed to fetch" while curl showed a healthy 200. OPTIONS
    now returns 204 with Allow-Methods: GET, OPTIONS and Allow-Headers
    including Cache-Control. The site build also drops the header, so either
    side alone fixes it.

v6 (weapons.php) - sends Cache-Control: no-store, so neither the browser nor
    the host CDN can replay the arsenal from before the save. The main site's
    Armory Browser also adds a cache-buster of its own.

v6/v8 (both) - the database password moved into armory-config.php. Both files
    ship with an empty password and refuse to connect with a message naming
    that file, instead of a generic 500. Output from that file is buffered and
    discarded, so a PHP warning there can never corrupt the JSON response.

Console - BUILD 2026-10-19.3 stages the picture when you pick it, sends the
    database an absolute URL (works when embedded, not just on the subdomain),
    and reads the record back after saving: "Image confirmed in database" or
    "IMAGE NOT STORED".
